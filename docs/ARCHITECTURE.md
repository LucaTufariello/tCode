# Architecture and native API decisions

The application separates editing, configuration, and executable syntax parsing:

- **TCodeCore** contains encoding/atomic filesystem operations, Unicode positions, indexing/search, recovery, process/protocol/Git operations, test parsing, the versioned language model/registry, catalog, tool/grammar installers, and XPC syntax interfaces. It has no UI dependency.
- **TCode** owns AppKit windows, native menus/panels, the editor/document pool, language recognition/selection, LSP presentation, task/debug/Git workflows, SwiftTerm PTY views, and SwiftUI Settings.
- **CTreeSitter** vendors the pinned Tree-sitter 0.25.10 runtime. **TCodeSyntax** owns grammar/query validation, Swift parser ownership, incremental trees, and UTF-16 capture conversion. Only **TCodeSyntaxService**, a bundled sandboxed XPC worker, links that parser into the running application. The editor process never maps a grammar module. **TCodeSyntaxProbe** is a validation executable, not an end-user tool.

## Documents and editor

`CodeDocument` owns one `NSTextStorage`, version, original bytes, encoding/BOM, shared UndoManager, recovery checkpoint, and language session. Split panes attach independent layout managers/text containers to that storage. Edits mutate native storage ranges; typing does not replace the entire buffer. The document pool canonicalizes symlink paths so the same file shares state across windows.

AppKit **NSTextView with TextKit 1** was selected deliberately. It provides mature native input methods, marked text, find/replace, selection, drag/drop, accessibility, and undo behavior, and supports attaching multiple layout managers to shared storage. A small native prototype and tests validated shared text/undo, multi-cursor insertion with IME fallback, Unicode, range edits, and large-file loading. TextKit 2's newer layout model would need a different shared document/layout implementation and was not adopted without validation. The choice is not a claim that TextKit 1 outperforms TextKit 2.

A native ruler draws visible line numbers and breakpoints. Syntax colors are temporary layout attributes. With an installed curated grammar, debounced document snapshots go to the syntax worker. It applies a UTF-8 edit to the prior tree, incrementally reparses, executes bounded structural queries, and returns UTF-16 captures. Split panes join one parse per document/version and share cached spans. Grammar/configuration changes invalidate pending work; stale results never replace newer highlighting. Basic regex highlighting remains available when a grammar is absent or parsing fails. Semantic tokens, query predicates, and embedded-language injections are deferred. Folding still suppresses selected glyphs without deleting text; it does not consume parser fold ranges. Native IME stays authoritative; secondary cursors clear when composition begins.

At **2,000,000 UTF-16 units**, large-file mode disables syntax scans, bracket searches, and LSP activation. Plain native editing and saving remain available. The measured 10.5 MB load covers decoding/storage, not full-document layout or scroll performance. Search skips files above 2 MB; indexing is capped at 50,000 paths; normal search returns at most 10,000 hits. Replacement scans all indexed eligible files and rejects a preview above 64 MB instead of applying a silently truncated plan.

## Tool processes and protocols

The native transport incrementally parses Content-Length messages with bounded headers/bodies. Actors serialize request IDs, matching, cancellation, timeout, errors, and notifications. Independent ordered reader and event streams allow DAP stopped-event handlers to issue requests without blocking response consumption. Server-initiated LSP file edits are sent through the same native review/preflight flow as rename/code actions. Unsupported resource operations are rejected. Advertised server commands require a concrete user review before execution.

The LSP layer negotiates UTF-16/UTF-8 positions (with UTF-32 mapping available), tracks versions, synchronizes the current text before requests, and drops stale results. Full-content change events are valid LSP synchronization messages; this implementation does not send minimal incremental deltas. Completion edits, including additional text edits, share one undo group. It advertises no snippet insertion support. Diagnostics and output locations are navigable. Ruff and server diagnostics are retained separately and merged so an empty server update cannot clear lint findings. Ruff scalar columns are converted to the negotiated LSP encoding; this was checked with a buffer containing a multi-scalar emoji.

## Language configuration and installation

Interface-version-2 language packs are Codable data in Core: associations, editor defaults/snippets, grammar references, LSP command/options/settings, formatter command, named multi-step tasks, debugger launch values, and installer recipe IDs. Version-1 JSON is migrated on decode; existing executable overrides, disabled-pack preferences, and `.tcode/run.json` remain valid. C/C++ shares one pack while using distinct `c` and `cpp` document IDs. Recognition ranks exact filenames, extensions, then first-line patterns; ties require a manual selection rather than guessing. Language choice persists for saved documents.

The registry overlays user JSON on three bundled defaults, then workspace `.tcode/languages` JSON only after explicit workspace consent. It validates configuration before activation and retains the last working file when a replacement is malformed. Reload works without recompiling or relaunching. It reports duplicate identities and invalid files. Imports contain data only, but commands in that data can execute when the user later requests a feature. Trust is therefore explicit for workspace overrides. Nothing runs simply because a folder or pack is opened. Tool-settings changes stop existing sessions; Enable Language Tools reconnects them. [Pack format and user workflow](LANGUAGE-SUPPORT.md).

The native Language Support page exposes independent recognition/highlighting/intelligence/formatting/tasks/debugging state. Installed and Catalog views share the registry. Bundled catalog metadata includes Python, C/C++, Swift, and on-demand Rust. Explicit refresh accepts a validated tCode GitHub Release catalog and atomically caches it for offline browsing. Published packs require checksums; draft entries may install their bundled configuration but do not promise published grammar downloads. No remote catalog or release is automatically published by the application or maintainer scripts.

`ToolInstallPlan` describes pinned downloads, hashes, prerequisites, destination changes, and whether setup can proceed. The user selects components and approves the concrete plan. Installer recipes are compiled into Core; a pack can reference recipe IDs but cannot inject an installation script. Healthy external tools are reused. New downloads stage in versioned tCode-owned directories; validation precedes atomic receipt activation. Failure/cancellation preserves prior active receipts. Python wheels are all hash-verified before an isolated CPython 3.12 environment is created and populated with `pip --no-index --no-deps`; `pip check`, executable probes, and native extension checks precede activation. The Rust language server uses a pinned native archive. Compilers, interpreters, Rust SDK components, and Xcode remain externally managed. Removal touches only tCode-owned resources and shows shared-pack impact.

Grammar archives pin source revision, arm64 module/query/archive hashes, runtime ABI, and licenses. The installer verifies contents and uses the actual sandboxed worker to compile queries and validate ABI before activation. It passes a read-only module file descriptor, source text, and query data over XPC; it grants no workspace path or network entitlement. Only the helper has the library-validation exception needed for curated downloaded code. Worker crashes/errors preserve the editor and reconnect on subsequent requests. See [syntax boundaries and packaged isolation checks](SYNTAX.md). This ad hoc distribution is not a substitute for a Developer ID/notarization release process.

This is not a general binary/plugin host. No VS Code extension package, Marketplace request, JavaScript extension runtime, AI provider, or remote coding service is involved.

`RunningProcess` performs blocking pipe reads off the UI thread, streams stdout/stderr, writes stdin concurrently, checks cancellation before/after launch, and signals its own child process group with TERM then KILL. Background search forwards parent cancellation to detached work. Formatters use stdout separately so stderr cannot become source text. Protocol sessions request orderly shutdown/disconnect. Quit awaits workspace shutdown before replying to AppKit; normal workspace closure cancels tools and terminal sessions.

Git invokes `/usr/bin/git` directly with argument arrays and parses NUL-delimited porcelain status, including rename records. It does not interpolate filenames or commit text into shell commands. Branch switching requires saved buffers and a clean Git workspace, then reloads clean documents. Unmerged files block commits.

## macOS 27 design

Verified against the installed macOS 27 SDK headers and Apple's current documentation:

- Native `NSToolbar`, `NSSplitViewController`, sidebar/inspector split items, and scroll views adopt system toolbar/sidebar and scroll-edge behavior. The code surface uses opaque `textBackgroundColor`.
- `NSGlassEffectView.effectIsInteractive` (macOS 27) is used on the small bottom-panel control header. It provides system Liquid Glass interaction without turning the editor into a translucent surface.
- `NSView.cornerConfiguration` and `.uniformCorners(radius: .containerConcentric(8))` (macOS 27) give that control container concentric system corners.
- SwiftUI Settings, system colors/fonts/SF Symbols, native dialogs/context menus, system focus rings, and standard accessibility controls retain platform behavior.

No custom continuous animation or rendering loop is used. System material/color behavior is used for accessibility preferences. Full VoiceOver and accessibility-setting audits are not claimed; see the validation matrix. The original AppKit-generated app icon is delivered as an `.icns` asset; layered Icon Composer variants are deferred.
